# Анализ потребления памяти и возможных утечек

В ходе анализа исходного кода проекта `OneSTools.EventLog` были выявлены несколько потенциальных причин высокого потребления памяти и возможных утечек.

## 1. Неограниченное кэширование метаданных (LgfReader)
**Критичность:** Высокая
**Место:** `OneSTools.EventLog/LgfReader.cs`

Класс `LgfReader` отвечает за чтение файла метаданных `1Cv8.lgf`. Он использует два словаря для кэширования всех найденных объектов:
```csharp
private Dictionary<(ObjectType, int), string> _objects;
private Dictionary<(ObjectType, int), (string, string)> _referencedObjects;
```
**Проблема:**
Эти словари наполняются по мере чтения файла и **никогда не очищаются**.
*   Файл `1Cv8.lgf` содержит определения всех пользователей, компьютеров, событий, таблиц и полей метаданных за всю историю существования информационной базы.
*   В крупных корпоративных системах размер этого файла может достигать сотен мегабайт.
*   При загрузке в память в виде объектов `string` и структур словаря, объем потребляемой памяти может в 2-4 раза превышать размер файла на диске.
*   Так как `EventLogReader` (и, следовательно, `LgfReader`) живет в течение всего времени работы службы экспорта, эта память никогда не освобождается.

**Рекомендация:**
Это архитектурная особенность, необходимая для быстрого поиска ссылок. Полностью исправить это сложно без потери производительности. Возможные пути оптимизации:
*   Использование интернирования строк (если много дублей).
*   Периодический перезапуск сервиса (воркаут).

## 2. Логическая ошибка и утечка в ExportersManager
**Критичность:** Средняя (Логическая ошибка + малая утечка)
**Место:** `OneSTools.EventLog.Exporter.Manager/ExportersManager.cs`

В методе `StopExporter` происходит отмена задачи, но **не происходит удаление записи из словаря** `_runExporters`.

```csharp
private void StopExporter(string id, string name)
{
    lock (_runExporters)
    {
        if (_runExporters.TryGetValue(id, out var cts))
        {
            cts.Cancel();
            _logger?.LogInformation($"Event log exporter for \"{name}\" information base is stopped");
            // MISSING: _runExporters.Remove(id); <-- ОШИБКА
        }
    }
}
```

**Последствия:**
1.  **Утечка памяти:** Объекты `CancellationTokenSource` накапливаются в словаре при каждом удалении/перемещении базы данных.
2.  **Логическая ошибка:** Если база данных была удалена (или временно недоступна), а затем снова появилась (с тем же путем), метод `StartExporter` **не запустит** экспорт, так как увидит, что ключ уже есть в словаре (хотя связанная с ним задача уже остановлена).

## 3. Высокая аллокация временных объектов (GC Pressure)
**Критичность:** Средняя
**Место:** `OneSTools.EventLog/LgpReader.cs`

При чтении событий (`ReadNextEventLogItemData` и `ParseEventLogItemData`) создается большое количество временных строк и объектов.
*   `BracketsParser.ParseBlock` создает новые строки для каждого поля события.
*   Метод `GetData` создает новые строки для представления данных.

При высокой скорости чтения (тысячи событий в секунду) это создает огромную нагрузку на Garbage Collector (GC). Если сервер имеет ограниченные ресурсы или GC не справляется, потребление памяти может временно скакать до высоких значений ("пила"), или постоянно расти при фрагментации кучи (LOH), если строки большие.

## 4. Некорректная реализация Dispose/Finalizer
**Критичность:** Низкая (Технический долг)
**Место:** `OneSTools.EventLog/EventLogReader.cs`

В финализаторе `~EventLogReader` вызывается `Dispose(false)`. Однако метод `Dispose(bool disposing)` не проверяет флаг `disposing` перед обращением к управляемым объектам (`_lgpFilesWatcher`, `_lgfReader`).

```csharp
protected virtual void Dispose(bool disposing)
{
    if (!_disposedValue)
    {
        // Ошибка: Обращение к managed объектам из финализатора
        _lgpFilesWatcher?.Dispose(); 
        // ...
        _disposedValue = true;
    }
}
```
Это может приводить к непредсказуемому поведению при завершении работы приложения (Crash), хотя вряд ли является причиной утечки памяти.

## Заключение
Основной причиной высокого потребления памяти ("съедает всю память"), вероятнее всего, является **пункт 1 (LgfReader)**. Если файл метаданных большой, приложение будет занимать много памяти "by design".

**План действий:**
1.  Исправить ошибку в `ExportersManager.cs` (удаление из словаря).
2.  Исправить паттерн Dispose в `EventLogReader.cs`.
3.  Для решения проблемы с `LgfReader` — проверить размер файла `1Cv8.lgf` на целевом сервере. Если он огромен, рассмотреть возможность оптимизации хранения строк.
